# Структура JSON / YAML, версии 1 и 2

Примеры: [JSON](example.json), [YAML](example.yaml). Оба файла описывают один процесс и преобразуются в один и тот же BPMN. Поддерживаются расширения `.json`, `.yaml`, `.yml` и `.ylm` (последнее трактуется как YAML). Кодировка UTF-8; BOM допускается.

| Поле | Обязательность и содержание |
| --- | --- |
| `schema_version` | Обязательно: число `1` |
| `process` | Обязательно: объект с `id`, `name` |
| `roles` | Непустой массив `{id, name}`; роли участников |
| `nodes` | Непустой массив `{id, type, name, role}`; `role` — id из roles |
| `flows` | Массив `{id, source, target}`; последовательность шагов, оба конца — id из nodes. Дополнительно `name` — подпись перехода, `condition` — точный текст условия |
| `documents` | Необязательный массив `{id, type, name}`; `type` — `document` (значок-ссылка на документ) или `store` (ссылка на базу/хранилище). Дополнительно `object_ref` или `store_ref` — ссылка на явно объявленное определение |
| `data_objects`, `data_stores` | Необязательные массивы `{id, name}` — самостоятельные логические определения, на которые ссылаются значки documents |
| `messages` | Необязательный массив `{id, name}` — глобальные определения сообщений |
| `associations` | Необязательный массив `{id, source, target}`; каждый элемент соединяет шаг с документом/базой. Направление шаг → документ означает выдачу, документ → шаг — использование |

Обязательны все поля вложенных объектов, перечисленные без пометки «дополнительно». Если необязательных массивов нет, они считаются пустыми. Прочие поля, повторные ключи и неизвестные типы отклоняются: их нельзя молча потерять. Значения строковых полей должны быть непустыми строками; для отсутствующей подписи перехода просто не указывайте `name`.

**id уникальны во всём файле** — у процесса, ролей, шагов, документов и связей. Разрешены латинские буквы, цифры, `_`, `.` и `-`; первый символ — буква или `_`. Префикс `__import_` зарезервирован. Названия `name` могут быть на русском и не задают порядок шагов. Положение в массиве также не задаёт бизнес-последовательность: её определяют только `flows`.

Типы узлов: `startEvent`, `endEvent`, `intermediateCatchEvent`, `intermediateThrowEvent`, `task`, `userTask`, `manualTask`, `serviceTask`, `sendTask`, `receiveTask`, `businessRuleTask`, `exclusiveGateway`, `parallelGateway`, `inclusiveGateway`. Роли задаются каждому узлу, включая события и шлюзы. Вложенные подпроцессы, граничные события и произвольные расширения не входят в этот JSON-профиль. Межпуловые сообщения задаются в версии 2.

Каждый документ/хранилище должен иметь хотя бы одну связь в `associations`. Документы не могут быть концами `flows`. В `startEvent` нельзя входить, из `endEvent` нельзя выходить. Циклы и ветвления описываются обычными переходами; генератор не выводит их из наименований.

Для условного ветвления используйте `exclusiveGateway` или `inclusiveGateway`:

```json
{"id": "decision", "type": "exclusiveGateway", "name": "Согласовано?", "role": "manager", "default": "rejected"}
```

Его исходящие переходы, например:

```json
[
  {"id": "approved", "source": "decision", "target": "pay", "name": "Да", "condition": "approved == true"},
  {"id": "rejected", "source": "decision", "target": "revise", "name": "Нет"}
]
```

`default` — необязательное поле шлюза, ссылающееся на его исходящий переход **без condition**. Узлы `pay` и `revise` должны быть объявлены в `nodes`. `name` — только подпись и не заменяет `condition`. Условие сохраняется как BPMN formalExpression, не выполняется и не переводится в какой-либо язык; синтаксис выбирается для вашей среды исполнения. Без `condition` шлюз тоже допустим как описательная схема. У `parallelGateway` и `startEvent` условие на исходящих связях запрещено.

Координаты, размеры и маршруты указывать не нужно и нельзя: их строит существующий алгоритм. Адаптер создаёт промежуточный `input_model.bpmn` с техническим DI, который полностью удаляется режимом `scratch` перед компоновкой. В результат включены промежуточный BPMN, `input_report.json` с хешем входа и количеством объектов, исходный JSON/YAML и обычные отчёты семантики/геометрии. Проверка сохранности бизнес-XML сравнивает итог с промежуточным BPMN; соответствие JSON/YAML ему покрывается проверками адаптера. XML не содержит скрытой логики, не заданной в структуре.

## Сообщения в событиях

`intermediateCatchEvent` — промежуточное ожидание; `intermediateThrowEvent` — промежуточная отправка. Можно явно задать сообщение для них, а также для startEvent/endEvent:

```json
{"id":"wait","name":"Получено подтверждение","role":"manager","type":"intermediateCatchEvent",
 "event_definition":{"id":"wait_definition","type":"message","message_ref":"confirmation"}}
```

`confirmation` нужно объявить в корневом messages: `{"id":"confirmation","name":"Подтверждение"}`. ID определения события также уникален. Без event_definition остаётся событие без определения; триггер не выдумывается из названия или входящего messageFlow. Для сообщения-ожидания рисуется двойной круг и незакрашенный конверт, для отправки — закрашенный конверт.

## Один документ, несколько ссылок

В `data_objects` объявите `{"id":"DO_Contract","name":"Договор"}`. Затем в documents:

```json
[
  {"id":"DO_Contract_ref","type":"document","name":"Договор при проверке","object_ref":"DO_Contract"},
  {"id":"DO_Contract_sign","type":"document","name":"Договор при подписании","object_ref":"DO_Contract"}
]
```

Каждой видимой ссылке нужны собственные associations. Определение становится BPMN dataObject с исходным ID, а две ссылки — dataObjectReference с отдельными исходными ID и общим dataObjectRef. Они не сворачиваются в один значок. Для хранилищ аналогично: `data_stores`, тип `store`, поле `store_ref`. Без object_ref/store_ref старое краткое описание создаёт отдельное определение автоматически.

## Версия 2: два самостоятельных процесса на одном полотне

Полные рабочие примеры: [JSON](example-collaboration.json), [YAML](example-collaboration.yaml).

Корень содержит **schema_version: 2**, `processes`, `collaboration` и необязательный `messages`. Один или два объекта processes имеют поля `id`, `name`, `roles`, `nodes`, `flows`; необязательные documents, associations, data_objects, data_stores остаются внутри своего процесса. В отличие от версии 1, отдельного process и общих roles/nodes/flows в корне нет.

```json
"collaboration": {
  "id":"Collab", "name":"Организация и заказчик",
  "participants":[
    {"id":"Org","name":"Организация","process_ref":"OrganizationProcess"},
    {"id":"Cust","name":"Заказчик","process_ref":"CustomerProcess"}
  ],
  "message_flows":[
    {"id":"M1","source":"send","target":"CS","name":"Комплект документов","message_ref":"msg_package"},
    {"id":"M2","source":"confirm","target":"wait","name":"Подтверждение"}
  ]
}
```

У каждого процесса ровно один participant; process_ref — его ID. Пулы без processRef и более двух процессов пока не входят в профиль. source/target у message_flows — ID операций, событий или пулов разных участников, а не документов/шлюзов. message_ref необязателен, но если задан — ссылается на messages. Условия относятся только к внутренним flows, а не к message_flows. Внутренние flows и associations не могут пересекать границу процесса. Начало/ожидание/receiveTask не могут отправлять messageFlow; конец/отправляющее событие/sendTask не могут быть его приёмником.

ID уникальны **во всей collaboration**, включая оба процесса и общие сообщения. Каждый процесс компонуется по собственному графу; затем пулы размещаются совместно, а отдельный маршрутизатор ведёт messageFlow с пунктиром, кружком на источнике и открытым наконечником. Пересечения учитываются в отчёте, совпадающие отрезки, прохождение через объекты и разрезание текста не допускаются. Бизнес-XML целиком, включая processRef, messageFlow, определения событий и ссылки на документы, проверяется до и после.
