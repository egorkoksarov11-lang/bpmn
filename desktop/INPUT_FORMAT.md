# Структура JSON / YAML, версия 1

Примеры: [JSON](example.json), [YAML](example.yaml). Оба файла описывают один процесс и преобразуются в один и тот же BPMN. Поддерживаются расширения `.json`, `.yaml`, `.yml` и `.ylm` (последнее трактуется как YAML). Кодировка UTF-8; BOM допускается.

| Поле | Обязательность и содержание |
| --- | --- |
| `schema_version` | Обязательно: число `1` |
| `process` | Обязательно: объект с `id`, `name` |
| `roles` | Непустой массив `{id, name}`; роли участников |
| `nodes` | Непустой массив `{id, type, name, role}`; `role` — id из roles |
| `flows` | Массив `{id, source, target}`; последовательность шагов, оба конца — id из nodes. Дополнительно `name` — подпись перехода, `condition` — точный текст условия |
| `documents` | Необязательный массив `{id, type, name}`; `type` — `document` (документ) или `store` (база/хранилище) |
| `associations` | Необязательный массив `{id, source, target}`; каждый элемент соединяет шаг с документом/базой. Направление шаг → документ означает выдачу, документ → шаг — использование |

Обязательны все поля вложенных объектов, перечисленные без пометки «дополнительно». Если необязательных массивов нет, они считаются пустыми. Прочие поля, повторные ключи и неизвестные типы отклоняются: их нельзя молча потерять. Значения строковых полей должны быть непустыми строками; для отсутствующей подписи перехода просто не указывайте `name`.

**id уникальны во всём файле** — у процесса, ролей, шагов, документов и связей. Разрешены латинские буквы, цифры, `_`, `.` и `-`; первый символ — буква или `_`. Префикс `__import_` зарезервирован. Названия `name` могут быть на русском и не задают порядок шагов. Положение в массиве также не задаёт бизнес-последовательность: её определяют только `flows`.

Типы узлов: `startEvent`, `endEvent`, `task`, `userTask`, `manualTask`, `serviceTask`, `sendTask`, `receiveTask`, `businessRuleTask`, `exclusiveGateway`, `parallelGateway`, `inclusiveGateway`. Роли задаются каждому узлу, включая события и шлюзы. Вложенные подпроцессы, граничные события, межпуловые сообщения и произвольные расширения не входят в эту версию формата.

Каждый документ/хранилище должен иметь хотя бы одну связь в `associations`. Документы не могут быть концами `flows`. В `startEvent` нельзя входить, из `endEvent` нельзя выходить. Циклы и ветвления описываются обычными переходами; генератор не выводит их из наименований.

Для условного ветвления используйте `exclusiveGateway` или `inclusiveGateway`:

```json
{"id": "decision", "type": "exclusiveGateway", "name": "Согласовано?", "role": "manager", "default": "rejected"}
```

Его исходящие переходы, например:

```json
[
  {"id": "approved", "source": "decision", "target": "pay", "name": "Да", "condition": "approved == true"},
  {"id": "rejected", "source": "decision", "target": "revise", "name": "Нет"}
]
```

`default` — необязательное поле шлюза, ссылающееся на его исходящий переход **без condition**. Узлы `pay` и `revise` должны быть объявлены в `nodes`. `name` — только подпись и не заменяет `condition`. Условие сохраняется как BPMN formalExpression, не выполняется и не переводится в какой-либо язык; синтаксис выбирается для вашей среды исполнения. Без `condition` шлюз тоже допустим как описательная схема. У `parallelGateway` и `startEvent` условие на исходящих связях запрещено.

Координаты, размеры и маршруты указывать не нужно и нельзя: их строит существующий алгоритм. Адаптер создаёт промежуточный `input_model.bpmn` с техническим DI, который полностью удаляется режимом `scratch` перед компоновкой. В результат включены промежуточный BPMN, `input_report.json` с хешем входа и количеством объектов, исходный JSON/YAML и обычные отчёты семантики/геометрии. Проверка сохранности бизнес-XML сравнивает итог с промежуточным BPMN; соответствие JSON/YAML ему покрывается проверками адаптера. XML не содержит скрытой логики, не заданной в структуре.
