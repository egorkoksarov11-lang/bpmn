# v23.5.0 — события, ссылки на документы, два процесса

Основание: пользовательский реестр `BPMN_Unsupported_Elements.json` описывает 8 исходных схем, 2 collaboration, 4 participants, 7 messageFlow, 2 intermediateCatchEvent, 2 дополнительных процесса и 18 частично представимых dataObjectReference. Это реестр конструкций, а не полные исходные бизнес-графы. Приложенных к реестру восьми BPMN XML нет, поэтому воспроизведение именно этих восьми схем не заявляется. Тесты используют отдельные синтетические графы, покрывающие перечисленные конструкции.

## Поддержка

- JSON/YAML: schema_version=1 сохранён; schema_version=2 содержит processes (один или два), collaboration, participants с process_ref и message_flows. Общие messages объявляют сообщения. ID глобально уникальны. Внутренние flows/associations принадлежат только своему процессу.
- intermediateCatchEvent/intermediateThrowEvent сохраняют тип; message event_definition сохраняет отдельный ID и message_ref. У ожидания — двойной круг и незакрашенный конверт; у отправки — закрашенный. Пустое определение события из исходного BPMN не заменяется задачей, не получает выдуманный триггер и отмечается в предупреждении.
- data_objects/data_stores задают определения с исходными ID; documents.object_ref/store_ref — независимые видимые ссылки с собственными ID и названиями. Несколько dataObjectReference одного документа не сворачиваются в один объект.
- BPMN XML с двумя процессами, одним collaboration и одним общим DI plane проходит через тот же новый слой компоновки. Сохраняются всё бизнес-XML и структура DI; допускается только изменение геометрии и расположения подписей.

## Алгоритм

Входной XML разделяется только на временные копии для компоновки, а не на новую бизнес-модель. Для каждого процесса вызывается прежний scratch backend со сбросом координат. Если у процесса отсутствуют роли, временная рамка помогает компоновке, но не переносится в выходной XML. Исходные процессы, роли, узлы, ссылки и условия остаются в оригинальном дереве.

Пулы размещаются вертикально; порядок — порядок участников в объявлении, а не названия/номера. Горизонтальный сдвиг второго процесса выбирается по медиане разностей координат концов сообщений уже построенных графов. Рамки содержат узлы, подписи и внутренние пути. Полосы ролей занимают ширину своего пула. Между пулами оставляется коридор, зависящий от числа сообщений.

Для messageFlow выбираются прямые и ортогональные варианты с раздельными портами; при необходимости используется A*. Препятствия — операции, события, документы, их подписи и заголовки ролей/пулов. Внутренние маршруты не перепрокладываются. Учитываются длина, изгибы, пересечения и тесные параллельные линии; совпадающие отрезки запрещены. Подписи сообщений размещаются после всех линий и проверяются на пересечения с текстом и фигурами. SVG рисует messageFlow пунктиром с кружком источника и открытой стрелкой.

## Проверки и ограничения

Проверяется полный canonical XML без BPMNDiagram, включая processRef, messageFlow, messageEventDefinition, dataObjectRef и ID. Дополнительно сохраняется структура DI. После записи проверяются каждый процесс, отсутствие наложений пулов, принадлежность фигур пулам, контуры концов, зазоры у фигур/заголовков, наложения отрезков и расположение подписей. Число пересечений и длина сообщений записываются в geometry_report.json; пересечения не скрываются и глобальный оптимум не заявляется.

234 теста прошли: сохранность двух процессов и всех связей, JSON/YAML-эквивалентность, две ссылки одного документа, обычное событие без определения, явные message definitions, процесс без laneSet, messageFlow с концом на participant, четыре и семь сообщений, отрицательные случаи неверных ID/ролей/межпроцессных sequenceFlow и повреждённый конец линии. Отдельно в Chromium проверены загрузка schema 2, завершение генерации и скачивание ZIP; ошибок JavaScript нет. Промежуточный и итоговый BPMN импортированы bpmn-moddle без предупреждений. Workflow Windows выполняет установку с нуля, BPMN, старый JSON/YAML, новый JSON/YAML и тесты нового слоя.

Ограничения: максимум два процесса; каждому нужен собственный participant с processRef. Пустые пулы, больше двух процессов, несколько DI plane, расширенные подпроцессы, boundaryEvent, группы и текстовые аннотации не поддержаны. Новый collaboration backend используется в режиме scratch; остальные экспериментальные backend не заявляются. JSON event_definition пока описывает только сообщение; существующие timer definitions в допустимом BPMN сохраняются старым путём. При невозможности построить проверенный результат приложение выдаёт журнал, а не удаляет связи.
