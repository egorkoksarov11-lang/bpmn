# От наблюдений к алгоритму чистой BPMN-компоновки

Продолжение исследования, 1 ноября 2026. Это проверка правил и прототип структурного распознавания. Новая компоновка №08 по этим правилам ещё не построена.

Главное уточнение: простота отдельных стрелок, малая площадь отдельного фрагмента и качество схемы целиком — разные цели. Их необходимо согласовывать через входы и выходы фрагментов. Нельзя сначала зафиксировать все пары «задача — шлюз», а затем ожидать, что трассировщик исправит расположение их внешних связей.

## 1. Локализован источник лишних изгибов

Для пары взята задача с единственным следующим узлом-шлюзом, у которого не менее двух различных последователей. Числа ниже — только пары в одной дорожке; ориентация определяется преобладающим смещением центров, а не направлением каждого сегмента стрелки.

| Положение шлюза относительно задачи | 32 референса | Итог вашей сессии | Автоматический №08 r2 |
|---|---:|---:|---:|
| Справа | 88 | 5 | 21 |
| Снизу | 12 | 5 | 0 |
| Слева | 11 | 1 | 0 |
| Сверху | 7 | 0 | 0 |

В референсах примерно четверть таких пар имеют другую ориентацию. В вашей сессии — больше половины. У автоматики все пары направлены вправо.

Простота входа в шлюз уже достигнута ценой сложности выходов:

| Внутридорожечные потоки | Ваш итог: число / изгибы | Автоматика: число / изгибы |
|---|---:|---:|
| Задача → шлюз | 11 / 2 | 21 / 0 |
| Шлюз → задача | 21 / 14 | 17 / 38 |

Следовательно, оценивать пару только по её внутренней прямой стрелке недостаточно. Ориентация выбирается по всем входам и выходам, включая отрицательные исходы, повторные входы и связи с другими ролями. Не следует искусственно добавлять два изгиба на выходе ради сохранения одной прямой внутри пары.

Это сравнение разных графов, поэтому оно локализует вероятную проблему, но не доказывает, что одни повороты шлюзов дадут №08 качество ручного примера.

## 2. Один графовый шаблон имеет несколько правильных геометрий

Независимо от названий и координат найдены три одинаковые внутренние конструкции:

`Проверить → Решение → Дополнительная проверка (Call Activity) → Решение о результате → Повторить проверку`.

Это четыре узла и четыре внутренние направленные связи. Типы узлов и принадлежность к одной дорожке совпадают. Внешние входы и выходы при этом различаются.

| Конструкция по ID входной задачи | Габарит фигур до → после | Длина внутренних стрелок до → после | Изгибы до → после |
|---|---|---:|---:|
| C2 | 618 × 76 → 570 × 171 | 1019,84 → 708 | 2 → 2 |
| C6 | 688 × 78 → 413 × 239 | 737 → 588 | 2 → 4 |
| Cnewcheck | 393 × 287 → 391 × 323 | 1085,5 → 501 | 2 → 1 |

Габарит здесь учитывает только фигуры четырёх узлов. Он не включает документы, подписи, внешние связи или выступающие маршруты; это не полная площадь блока для упаковки.

Наблюдение уточняет прошлый ориентир «увеличивать долю прямых стрелок»: в конкретном фрагменте C6 вы допустили больше изгибов, но сократили расстояния. В двух конструкциях местная площадь фигур увеличилась. Поэтому правила «любой новый изгиб плох» и «площадь каждого блока обязана уменьшаться» неверны.

Интерфейс конструкции также важен: у C2 один внешний вход, у C6 три. У каждого по три выходящих связи. Все отдельные рёбра должны сохраняться. Геометрический шаблон с одним нарисованным входом нельзя механически применять к варианту с тремя входами.

Правило для генератора: один распознанный тип конструкции порождает несколько вариантов геометрии с явным списком внешних портов. Выбирается вариант в окружении соседей, а не один «канонический рисунок» для всех случаев.

## 3. Возврат нельзя определять по координатам

В 32 референсах найдено 157 направленных влево связей по центрам узлов. Из них 68 вообще не входят в направленный цикл. Значит, как минимум эти 68 связей нельзя объявлять возвратами только из-за направления влево.

В вашем итоговом примере таких связей 18, из них 11 вне циклов. Среди них обычные продолжения и передачи между ролями.

Проверен текущий backend: отражение исходной геометрии по X без изменения графа меняет состав его `feedback_edges` на 32 ребра в ручном примере и на 39 в frozen №08. Это диагностические подсказки для отображения, а не семантический поиск циклов. Их нельзя использовать как универсальный классификатор бизнес-возвратов или указание отправить ребро к периметру всей схемы.

В новом прототипе кандидат возврата определяется по графу: целевой узел доминирует над исходным, то есть любой путь от входа к исходному проходит через целевой. Затем собирается тело естественного цикла. Для сложных циклов с несколькими входами такой шаблон не навязывается.

Узлы без достижимого входа или выхода отмечаются отдельно. Замкнутый периодический процесс не получает придуманного стартового/конечного события ради удобства анализа.

## 4. Крупные циклы и пересекающиеся блоки требуют осторожности

В ручном примере четыре циклические компоненты по четыре узла — они удобны как локальные конструкции.

В №08 две компоненты: четыре и 57 узлов. В сумме этим двум циклическим компонентам принадлежит 91 из 95 потоков графа. Сворачивание такой компоненты в один «блок возврата» скроет почти весь процесс и не поможет компоновке.

Прототип отдельно находит в №08 17 естественных циклов по обратным рёбрам, включая небольшие тела из трёх–пяти узлов. Они могут быть вложены, пересекаться или иметь одинаковое тело при разных обратных рёбрах. Это 17 кандидатов, а не 17 непересекающихся блоков. Нужен выбор совместимого покрытия и иерархия: локальные конструкции внутри более крупных сценариев, с внешними портами на каждом уровне.

Аналогично проверены развилки с общим последующим узлом. На 32 референсах найдено 129 кандидатов «разветвление → общее продолжение», но только 65 проходят консервативную проверку единственного входа и выхода для области, включающей оба граничных узла. Остальные имеют внешние связи, которые нельзя спрятать при свёртке. Не каждый кандидат является независимым прямоугольником для упаковки.

Общий последующий узел найден анализом постдоминирования на путях к существующим выходам. Если такого узла нет, алгоритм не создаёт шлюз слияния. Бесконечные исполнения и особые механизмы событий требуют отдельной обработки; это структурная подсказка, а не доказательство поведенческой эквивалентности.

## 5. Простые правила, которые референсы не подтверждают

### «Да всегда продолжает основной путь прямо»

Проверены XOR-шлюзы с одним входящим ребром и не менее двумя исходящими. Учтены только точные подписи Да/Нет/yes/no. Продолжением считается совпадение направления последнего входящего и первого исходящего сегмента.

- Из 115 выходов «Да» прямо продолжаются 44 — 38,3%.
- Из 113 выходов «Нет» прямо продолжаются тоже 44 — 38,9%.

Это не определение основного бизнес-сценария. Геометрия выхода зависит от окружения. Подписи нельзя переставлять между рёбрами, чтобы подогнать схему под привычную форму развилки. У одного шлюза может быть три и более исхода; сводить его к бинарному «Да/Нет» запрещено.

### «Все повторяющиеся конструкции рисуются одинаково»

Три одинаковых внутренних графа проверки в одной сессии имеют разные геометрии и разные внешние входы. Нужна библиотека вариантов и правило выбора, а не копирование координат.

### «Каждое улучшение уменьшает местную площадь и число изгибов»

Пример C6 опровергает оба требования. Конструкция становится выше, внутренние связи короче, а внешние связи могут подключаться удобнее. Причинную роль каждого перемещения отдельно запись сохранений не устанавливает: несколько объектов менялись одновременно.

### «Для компоновки достаточно распознать все циклические компоненты»

Большая компонента №08 содержит 57 узлов. Нужен более мелкий разбор; одно лишь разбиение на компоненты слишком грубо.

## 6. Набор конструкций для первой библиотеки

Это внутренние конструкции layout-планировщика. Они не добавляют BPMN-элементы и не меняют тип существующих узлов.

| Конструкция | Признаки по графу | Варианты геометрии | Что обязательно сохраняется |
|---|---|---|---|
| Последовательная цепочка | Внутренние узлы без дополнительного входа/выхода sequenceFlow | Вправо, вниз, продолжение влево на другом ряду | Все задачи и документные связи; порты границ цепочки |
| Задача с решением | Один следующий шлюз с несколькими различными продолжениями | Шлюз с четырёх сторон; ориентация текста обычная | Тип шлюза, все входящие/исходящие рёбра, условия и default |
| Запрос исправления | Естественный цикл, часто с передачей другой роли | Короткий местный прямоугольный/U-образный обход | Исходные исполнители и точка повторного входа |
| Дополнительная проверка | Цикл «задача → решение → Call Activity → результат → повтор» | Несколько ориентаций по входам/выходам | Тип Call Activity, все ветви допуска/отказа и повторов |
| Развилка с общим продолжением | Подтверждённый общий последующий узел | Ветви рядом, короткий подход к общему узлу | Внешние входы в ветви; существующий механизм слияния |
| Общий отказ/уведомление | Несколько входов к одной существующей задаче | Область сбора потоков рядом со связанными проверками | Одна общая задача; её нельзя дублировать ради красоты |
| Передача между ролями | У существующей связи разные lane membership | Прямая, L- или Z-маршрут с зарезервированным коридором | Роли и направление связи |
| Документ с несколькими связями | Один объект/хранилище связан с несколькими задачами | Соседняя свободная область, короткие association | Все ссылки и направления; нельзя удалить или размножить объект |
| Короткое завершение ветви | Ветка действительно достигает endEvent | Завершение рядом с веткой с местом под подпись | Все существующие конечные события и их типы |

Повторяемость уже подтверждена: один небольшой цикл «задача → решение → исправление другой ролью → повтор» с точным сохранением типа task найден девять раз в семи из 32 референсов. Варианты с userTask распознаются отдельно. Общая геометрия может использоваться повторно, но BPMN-типы не заменяются друг другом.

Для параллельных и событийных развилок нужны отдельные допустимые шаблоны. Совпадения формы графа недостаточно, чтобы трактовать parallelGateway как exclusiveGateway. Анализатор сохраняет различие типов. Событийные прерывания, messageFlow, boundaryEvent и compensation пока не охвачены полноценной грамматикой поведения.

## 7. Как должен работать выбор компоновки

### Шаг 1. Зафиксировать исходную модель

Полный семантический snapshot и DI-структура. Отдельно зафиксировать все подписи, default, условия, вложенные ассоциации, роли и границы subprocess. Анализировать внутренности subprocess в собственном графе. Не создавать виртуальные элементы в сохраняемом BPMN; технические корни/границы существуют только в планировщике.

### Шаг 2. Распознать кандидаты по графу

Сначала маленькие проверяемые конструкции и их логические интерфейсы. Координаты исходника могут помогать сохранять привычный порядок, но не определяют наличие цикла. Названия не определяют тип узла или истинность ветви.

Каждый кандидат содержит:

```text
nodes: исходные ID узлов
internal_edges: исходные ID внутренних рёбер
boundary_ports: edge ID + sourceRef + targetRef + вход/выход
lane_requirements: фиксированные роли
geometry_variants: допустимые размещения, без поворота текста
label_and_document_reservations: области для подписей и документов
```

Кандидаты проверяются на пересечения друг с другом и на внешние связи. Нельзя одновременно назначить один узел двум независимым блокам. Вложенность допускается только явно, с согласованными портами родителя и ребёнка.

### Шаг 3. Выбрать совместимые конструкции и несколько общих планов

Сначала сформировать несколько вариантов целой схемы по расположению сценариев. У каждого должны быть понятны входы и выходы. Не фиксировать основной путь и порядок колонок навсегда: в текущем `block_optimize.py` backbone заблокирован для перемещений, что ограничивает перестройку основных частей.

Внутри дорожек допустимы разные начала колонок, короткие вертикальные продолжения и локальные ряды. Полностью общая сетка не обязательна. Порядок дорожек сохраняется по умолчанию; высота определяется их содержимым и проходящими связями.

### Шаг 4. Совместить положение и трассировку

Быстрая оценка должна учитывать реальные порты и хотя бы пробные маршруты. После первичной трассировки трудная группа стрелок возвращается в планировщик: можно сместить или переориентировать связанные блоки. Повторная трассировка без изменения размещения — только один из доступных шагов.

Выбирать не просто кратчайший путь отдельной стрелки, а понятный набор путей: разные выходы шлюза различимы; входы общего узла не маскируют друг друга; возвраты обходят локальную конструкцию; межролевые передачи имеют свободные коридоры; нет общих наложенных сегментов.

### Шаг 5. Учесть подписи и документы до окончательной доводки

Полный текст измеряется выбранным шрифтом. Подписи условий закреплены за исходными ID рёбер. Документ выбирает место с учётом всех потребителей. Association имеет собственные кандидаты прямой геометрии, включая диагональную, с проверкой пересечений фигур и подписей.

Если чистого места нет, надо пересмотреть размещение блока. Уменьшение шрифта не является первым средством исправления.

### Шаг 6. Улучшать связанные участки, сохраняя лучший полный результат

Перемещения нескольких узлов и маршрутов оцениваются совместно. Рабочая перестройка может временно ухудшить показатель. К выдаче допускается только полный кандидат, прошедший все жёсткие проверки. Хранится несколько разных компромиссных вариантов, чтобы один произвольный набор весов не спрятал плохую геометрию.

## 8. Что считать обязательным и что оптимизировать

Жёсткие условия:

- Полная сохранность бизнес-логики, подписей, ролей, документов, типов и DI-структуры.
- Нет наложений фигур и общих наложенных сегментов разных стрелок.
- Нет линий через посторонние фигуры и текст.
- Корректные концы на контурах; все рёбра и все объекты присутствуют.
- Полный читаемый текст; отсутствие обрезки и неоднозначного расположения подписей.
- Ортогональные sequenceFlow; тип документной связи проверяется отдельно.

Оптимизируемые свойства оцениваются на уровне локального блока и схемы целиком:

- Понятность перехода между участками и между ролями.
- Контакты/пересечения с учётом их места: около шлюза и подписи они особенно мешают чтению.
- Простота маршрутов и локальность возвратов.
- Длина связей и площадь с нормированием на размеры фигур.
- Баланс свободного места: коридоры нужны, большие пустоты нежелательны.
- Стабильность расположения при небольшом изменении исходной модели.

Вес «один контакт = столько-то изгибов» ещё не установлен по человеческим предпочтениям. Обнаруженный компромисс C6 показывает, почему нельзя заменить оценку одним максимизируемым процентом прямых линий.

Критерий завершения — отсутствие нарушений и улучшение сравнимых полных вариантов. Заявлять «все оставшиеся пересечения неизбежны» без доказательства нельзя. Для печати проверяется физический размер текста, а не только отношение сторон листа.

## 9. Что уже реализовано для проверки понимания

Добавлен автономный анализатор `tools/analyze_layout_patterns.py`. Он читает исходные BPMN, распознаёт графовые конструкции, сохраняет их внешние связи, измеряет ориентации пар и геометрию маршрутов. Он не меняет XML и пока не является layout backend.

Проверены 12 тестов: истинное общее продолжение ветвей, разные окончания без выдуманного слияния, естественный цикл, цикл с несколькими входами, сохранение внешних портов, независимость распознавания от переименования ID/порядка рёбер, замкнутый недостижимый цикл, разделение областей subprocess, отклонение перехода между областями, сохранение типа шлюза и разбиения по ролям в шаблоне.

```bash
python tools/analyze_layout_patterns.py \
  --corpus /path/to/human-bpmn \
  --human /path/to/gold_reference_000017.bpmn \
  --automatic /path/to/process_08_v23.bpmn \
  --output /path/to/separate-analysis

python -m pytest -q tests/test_graph_patterns.py
```

Распознавание кандидата не доказывает поведенческую эквивалентность его свёртки. Небольшие шаблоны, сложные циклы и внешние порты помечаются отдельно, а изменения BPMN не выполняются.

## 10. Следующий проверяемый эксперимент

Ввести несколько ориентаций для пары с решением и небольших циклов, оценивать все их внешние связи, разрешить перестановку основной части схемы. Сравнить на одном frozen №08:

1. Текущий backend.
2. Только разные ориентации пар.
3. Ориентации плюс целые локальные проверки/возвраты.
4. То же с совместной переупаковкой соседей после пробной трассировки.

Для каждого варианта — одинаковые бизнес-узлы, роли, документы, шрифт и лимит времени. Отдельно показать контакты, изгибы после шлюзов, длины межролевых передач, площадь и жёсткие нарушения. Такой эксперимент проверит найденную причину, а не просто даст ещё один удачный случай подбора координат.
