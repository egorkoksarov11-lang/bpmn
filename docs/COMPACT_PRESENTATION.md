# Компактное представление и близость ролей

Проблема схемы №4 — 71 информационная связь от 18 объектов, часто повторяющая уже понятное обращение к документу. Пользователь разрешил убрать такие повторы и попросил сблизить постоянно взаимодействующие роли. Результат хранится отдельно от полной исходной модели.

## Два разных этапа контроля

`compact_process.py` сначала строит явную проекцию документов. До изменения записывается закрытый список удаляемых dataObjectReference/associations и соответствующих DI-объектов. Не удаляются определения dataObject/dataStore, задачи, события, шлюзы, роли или sequenceFlow. Сравнение исходной и итоговой модели после исключения только разрешённых элементов должно совпасть полностью.

После этого подготовленная проекция замораживается; компоновка меняет только DI. Полное business-XML equality в `semantic_diff.json` относится к **подготовленной проекции и итоговому рисунку**. Оно не означает равенства исходнику до согласованного удаления документных связей. `presentation_audit.json` явно разделяет эти сравнения, а Локальный `document_changes.json` содержит весь исходный XML удалённых элементов; публичная копия содержит только ID и причины изменений. Полный исходник и полный XML-журнал сохраняются локально. Они не включаются в публичную поставку; опубликованный журнал содержит ID и причины исключения.

Обычные `run_v23.py` и `ScratchBackend` без нового режима не удаляют ни документы, ни ассоциации. Упрощение не включается скрыто в чистый layout backend.

## Правила документов

Группировка выполняется по логическому dataObjectRef/dataStoreRef и явному состоянию документа. Совпадение названий не доказывает идентичность. Различные состояния и разные логические документы сохраняются. Для каждой группы выбирается одна связь с содержательной операцией; последующие обращения опускаются из представления и перечисляются в журнале.

Если есть явный производитель, документ показывается около первого производителя. Когда несколько участников собирают комплект или альтернативные ветки создают один результат, предпочтительна первая общая принимающая операция после начальных производителей. Возвраты исключаются только из анализа первого появления: ни один переход процесса не удаляется. Для уже существующего хранилища используется первое содержательное обращение.

Ссылки, участвующие в отношениях между самими документами, защищены от автоматического удаления. Произвольные дополнительные удаления требуют явного списка ID и причин через `--omit-documents reviewed.json`. Алгоритм не угадывает эквивалентность по похожим финансовым названиям.

В №4 убран один отдельный значок `DO_PaymentInstruction`: состав реквизитов уже показан в `DO_PaymentReady`, а их передача полностью описана в `T511_CM`. Определение данных сохранено. Допуск организации, согласование конкретной операции, банковский документ и подтверждение фактического получения платежа остаются разными объектами.

## Порядок ролей

После размещения внутри ролей измеряются реальные высоты дорожек и вертикальные положения концов каждого межролевого sequenceFlow. Оптимизируется сумма вертикальных расстояний этих концов. Это вертикальная часть нижней границы длины маршрутов; горизонтальная часть при перестановке целых дорожек неизменна.

Для ≤13 ролей используется точное динамическое программирование по подмножествам. Стоимость добавления очередной дорожки состоит из полных пересечений её высоты связями между уже размещёнными и следующими ролями и расстояний от границ до собственных концов связей. Для больших наборов применяется детерминированный поиск вставками. Точное решение сравнивается тестом с независимым полным перебором.

Вместе с дорожкой перемещаются её операции, документы и подписи; внутренние расстояния, типы и исполнители сохраняются. Затем все маршруты строятся заново и проходят строгие проверки. Явный порядок можно передать через `--role-order L1 L2 ...`.

Это не глобальная оптимизация всех обходов препятствий и пересечений. Метрики реальных маршрутов оцениваются отдельно.

## №4 v2

Операции/контрольные узлы: 69; переходы: 86; роли: 9. Информационные объекты: 18 → 17; их связи: 71 → 17. Ни один документ не соединяется с несколькими операциями. Один знак документа удалён, 54 повторные информационные связи исключены из проекции.

Порядок сверху вниз: Операционист → Уполномоченное лицо → Касса → Руководитель финансового блока → Клиентский менеджер → Факторинговая компания → Клиент → Главный бухгалтер / бухгалтерия → Кадровик / HR. Клиентский менеджер соседствует с обеими наиболее связанными ролями.

Суммарная длина 45 реальных межролевых переходов уменьшилась с 66 670,6 до 29 737,65 (−55,4%); самый длинный — 3 180,2 → 1 602,85 (−49,6%). Суммарная длина всех sequenceFlow — 80 338,8 → 40 542,55 (−49,5%). Это совокупный результат перестановки ролей, удаления информационных пучков и новой компоновки с коэффициентом расстояний 1,3 вместо прежнего 1,6.

Для выбранного размещения одна перестановка ролей уменьшает вертикальную целевую функцию с 49 717,85 до 26 511,55 (−46,7%). Прочие данные и координаты исходного рисунка в планирование не поступают.

139 тестов прошли за 41,55 секунды. Отдельно подтверждены полный видимый текст, порты, зазоры, отсутствие пересечений объектов/подписей, предел изгибов, корректность XML и точное соответствие списку разрешённых изменений. Не заявляются печать на одном A4, отсутствие всех пересечений линий или достижение качества всех ручных эталонов. Корпусные показатели r10 относятся к прежнему запуску; новый режим на всём корпусе не оценивался.
