# r10 — построение с нуля

Основной режим `scratch` строит схему после полного удаления подсказок расположения. Исходные координаты, размеры, маршруты и Bounds подписей не поступают в планирование. Размеры операций заново вычисляются по полному названию. Роли, типы, условия и все документные связи сохраняются.

Эталон используется для последующего сравнения. Уточнение уже готовой DI-геометрии остаётся отдельным явно выбираемым режимом `reference`; его результаты не доказывают построение с нуля.

## Что изменилось

- Вход планировщика — каноническая геометрия с одинаковыми центрами всех узлов, без исходных подписей и маршрутов. Это также исключает ложное определение обратной связи из-за разной ширины блоков.
- ELK Layered предлагает порядок слоёв. Основной продуктивный путь дополнительно выравнивается в последовательность операций; короткие ответвления получают отдельные места. Бизнес-переходы при этом не добавляются и не удаляются.
- Передачи между ролями могут занимать общий вертикальный столбец. Независимые сценарии упорядочиваются с учётом явных информационных зависимостей; числовые префиксы названий служат дополнительной подсказкой порядка.
- Документ с подписью размещается как отдельный блок около связанного шага. Основные коридоры последовательности резервируются раньше документов. Общие объекты сохраняют все потребляющие связи.
- Ряды уплотняются по занятым колонкам: свободные области документов могут совмещаться по высоте. Каждый результат затем полностью трассируется и проверяется.
- Шрифт и переносы рассчитываются по реальным метрикам Open Sans. Полные имена операций, документов, событий, шлюзов и именованных ветвей проверяются в сохранённом SVG. Пустые углы ромба не считаются занятым прямоугольником.

При выборе варианта учитываются контакты, последовательность чтения, изгибы, плотность линий и площадь. Устранение одного контакта не должно автоматически оправдывать большой обход.

## Проверка независимости от референса

`tools/verify_geometry_erasure.py` полностью меняет исходные координаты, размеры, waypoints и Bounds подписей и требует идентичного входа планировщика. Дополнительные интеграционные тесты сравнивают уже построенные схемы при разных исходных DI. Измерения исходного референса в основном pipeline выполняются после реконструкции.

В испытаниях `scratch-human` и `scratch` оба режима получают вход после полного сброса геометрии. Внешний incumbent запрещён. Все неуспехи и индивидуальные ухудшения должны оставаться в отчёте.

## Текущий статус

Опубликован промежуточный пример [BPMN](../examples/from_scratch/ref_11/from_scratch.bpmn) и [SVG](../examples/from_scratch/ref_11/from_scratch.svg), построенный с нуля. Полный прогон корпуса и итоговый отчёт находятся в работе. Достижение 80% визуального сходства пока не подтверждено; диагностический балл не подменяет визуальную оценку.

Исходные архивы, офисные документы и сырая запись работы не публикуются. Входная v22 не изменяется.

## Воспроизведение

```bash
npm ci
python -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python run_v23.py --input inputs/benchmark/process_08_v4_frozen.bpmn --output-dir scratch-result --layout-engine scratch --candidate-timeout 30
```

Режим `scratch` выбран по умолчанию. Для сохранения геометрии явно выберите `--layout-engine reference` либо прежний `adaptive`.

Исследованные основы: [ELK Layered](https://eclipse.dev/elk/reference/algorithms/org-eclipse-elk-layered.html), [bpmn-auto-layout](https://github.com/bpmn-io/bpmn-auto-layout), [bpmn-moddle](https://github.com/bpmn-io/bpmn-moddle). В текущем новом построителе ELK используется для предложения структуры, а трассировка и проверки выполняются кодом v23.
